# Webshop sample

Five Spring Boot 3.5 WebFlux services that call each other over HTTP, a shared library,
and an end-to-end module, built by one Maven reactor:

```text
common          Money, OrderPlaced event, ApiError, correlation-id WebFilter (auto-configured)
catalog         functional router: GET /products, /products/{sku}
pricing         @RestController POST /quotes; bulk and category discounts, tax
inventory       stock ledger, reservations that expire unless confirmed
orders          WebClient calls to catalog, pricing and inventory with timeouts and retries,
                POST /orders, server-sent event stream /orders/events
notifications   follows the orders event stream, reconnects, sends one email per order
system-tests    ShopSystemIT boots all five services on random ports and buys things
```

The services share no code except `common`, so the module graph is a star:
`system-tests` depends on every service, and every service depends on `common`. Tests
mix plain unit tests, `StepVerifier` with virtual time, `WebTestClient` bound to a router
function, `@WebFluxTest`, `@SpringBootTest` against Reactor Netty stub servers
(`OrderFlowIT`, `OrderEventsListenerIT`), and the system test.

`impact.json` was generated by `sieve init` and sets `"class_level": true`.

## What applying Sieve found

- `ShopSystemIT` starts the services with `SpringApplicationBuilder`, not a Spring test
  annotation. Class-level selection did not treat it as a container test, so a catalog
  price change selected only the catalog tests. They passed, the order total in the
  system test did not, and the selected run was green. Sieve now treats tests that call
  a container's bootstrap API as container tests.
- Maven's `-am` compiles the tests of upstream modules too. They stay skipped but were
  reported in `tests`; the selection now lists only tests in modules that run.
- A mutation that stopped publishing order events made `OrderServiceTest` wait forever
  on the event stream. The sample now bounds that wait and sets a 60 s JUnit default
  timeout, because a hung selected run costs more than the full suite.

## Replay

`demo.sh` copies the sample into a temporary Git repository, commits typical changes
(half of them bugs, each followed by its revert), and runs `sieve replay --run`: every
commit runs the full suite and the selection, and `missed` counts tests that failed in the
full run but did not run in the selection. Failing tests do not stop the reactor
(`-Dmaven.test.failure.ignore=true`), so the full run reports every failure.

```sh
cargo build --release
SIEVE=$PWD/target/release/sieve samples/webshop/demo.sh
```

- Selected runs took 44% less time and executed 314 of 1,083 test cases (29%). Every
  test class that failed in the full run also ran in the selection.
- A change inside one service runs the tests in that service that reach it, plus
  `ShopSystemIT`, which starts every service. Changing a test runs only that test
  (`OrderFlowIT`).
- `common` is used by everything. A change there selects nearly all tests and costs a
  few seconds more than the full suite, because class-level selection builds twice.
- A resource change (`application.properties`) keeps module-level selection: the
  catalog and system tests.
- In the inventory commit the full run also failed `ShopSystemIT` with HTTP 500s. The
  laptop slept during that run, and orders reused a pooled connection that inventory had
  closed (`PrematureCloseException`). Reservations are deliberately not retried. The
  selection ran the same test, which passed, so it is not a miss.
